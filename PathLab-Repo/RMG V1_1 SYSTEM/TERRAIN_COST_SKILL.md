# Skill：为 RMG V1.1 增加地形代价与不可跨越属性

> 当前实现状态：已在 `src/MapTerrain.cs`、`src/MapGenerator.cs`、`src/MapSkeleton.cs`
> 落地。`--cells PATH` 输出逐坐标 CSV；θ `--export` 自动写同名 `.cells.csv`。
> 可通行格代价为 1，不可跨越格 `cost=null`。

## 目标

在现有地图随机生成器脚本中，为每个地图坐标对应的地形增加通行属性，支持两种基本形式：

1.  **可通行且具有代价**：格子可以被结构路径经过，并附带有效的数值代价。
2.  **不可跨越**：格子不能被结构路径经过，不能仅用一个很大的代价值代替。

本任务只修改地图数据表达与相关数据传递，不实现游戏运行时寻路系统。

## 不可违反的约束

-   **不得改变原有地图生成机制。**
    保留现有随机生成流程、参数含义、随机数调用顺序（除非为实现数据赋值确有必要，并且已明确说明）、出怪口/入怪口生成规则、自然障碍生成规则、路径形状约束、地图结构优化和验证流程。
-   不得擅自重写或替换原有地图生成算法。
-   不得新增 A\*、Dijkstra 或其他游戏运行时寻路系统。
-   生成器内部已有的路径仅用于辅助地形结构生成、结构分析和验证。保留其原有职责；不要把它改造成游戏运行时寻路。
-   不要求改变文本/控制台地图的显示形式。文本符号输出不是本任务重点。
-   **必须修改坐标数据输出**：每个输出坐标都必须能对应到其地形类型，并携带该地形的通行属性；可通行地形还必须携带代价，不可跨越地形必须明确标记为不可跨越。
-   不要只在最终输出时临时猜测代价；属性必须在地图数据模型中有明确归属，并能从地形生成过程传递到坐标输出。
-   优先扩展现有类和数据结构，不要创建与现有地图状态重复、容易不一致的第二套格子数据模型。
-   不要顺手修改无关功能、格式、命名或架构。

## 开始修改前：先阅读项目

先检查并追踪以下内容，按实际项目文件名定位，不要假定文件一定存在：

1.  地图格子/坐标的数据结构。
2.  主地图生成器及其初始化、地形生成、自然障碍放置流程。
3.  内部结构路径的生成、保存、分析和验证逻辑。
4.  地形类型、自然障碍、特殊格子和出入口的现有表示方式。
5.  最终坐标信息的输出位置及其数据来源。
6.  配置参数、示例配置、测试和调用入口。

先画清数据流：**地形/格子如何生成 → 地形类型如何确定 →
内部路径如何读取地图 → 坐标数据如何输出**。在此基础上做最小范围修改。

## 数据模型要求

在现有格子数据结构中，为每个坐标对应的格子提供等价于以下语义的字段。字段名称应遵循项目现有命名风格，不要求照抄示例：

-   `TerrainType`：地形类型，优先复用项目现有地形类型。
-   `TraversalType` 或等价字段：明确表示可通行或不可跨越。
-   `Cost` 或等价字段：可通行地形的自身代价。

可采用枚举，例如：

``` csharp
public enum TraversalType
{
    Traversable,
    Impassable
}
```

如果项目已有等价枚举或布尔字段，优先复用，不要重复定义。

### 属性语义

-   **可通行地形**：必须明确标记为 `Traversable`，并具有有效代价。
-   **不可跨越地形**：必须明确标记为 `Impassable`。不要通过
    `Cost = 999999`、负数或其他魔法数表达不可跨越。
-   可通行地形的代价必须遵循项目既定的数值规则。若项目尚无规则，新增配置并使用清晰、可验证的默认值；不要擅自引入复杂的代价平衡机制。
-   如果现有算法要求代价为正数，则验证
    `Cost > 0`。若项目原有规则不同，先遵循并说明原规则。
-   对不可跨越格，`Cost` 可以设为
    `0`、默认值或可空值，具体选择应与项目语言版本和数据风格一致；关键是所有读取者必须先检查通行属性，不能将该值当作有效通行代价。
-   不要把"是否为自然障碍"与"是否不可通行"强行合并。若项目需要区分自然障碍、边界、出入口、特殊地形等来源，应保留各自的地形/来源信息。
-   每一个最终输出的地图坐标都必须有确定的地形类型与通行属性，不允许漏填、依赖未初始化的默认状态，或在不同输出阶段产生冲突。

## 赋值规则

在原有地图生成流程中，找到每一种地形实际被创建或确定的位置，并在同一数据流中写入对应属性。

建议采用以下原则：

1.  初始化格子时，赋予安全且明确的默认状态，避免未赋值。
2.  原有流程确定格子地形类型后，同步设置通行属性和代价。
3.  当原有流程把格子改成另一种地形时，必须同步更新地形类型、通行属性和代价，防止残留旧属性。
4.  出怪口、入怪口及其他特殊格子应依据原项目机制决定其通行属性，不可一概按普通地面处理。
5.  自然障碍的属性必须与原有障碍生成结果一致；不要因为增加属性而改变障碍生成概率、数量、位置或结构。
6.  若项目支持多种可通行地形，每种地形都应有明确的代价来源，例如现有配置、地形定义或集中式映射。避免在多处散落硬编码。
7.  如果同一地形存在多个生成入口，确保所有入口都能赋值，不要只修改最常见的一条分支。

可以将赋值封装成小型辅助方法，但应保持最小改动；不要为了封装而重构原有生成流程。

## 内部结构路径的处理

原有内部路径是地形结构生成的辅助数据，不是游戏运行时寻路模块。

-   保留路径的原始生成与使用目的。
-   原有路径只按几何关系或原有规则构造时，不要擅自改为代价最小路径。
-   原有路径检查是否经过障碍时，可在不改变判定语义的前提下读取新的通行属性；也可以继续读取既有障碍字段，但必须保证两者一致。
-   只有当原有生成算法本身已经使用地形通行/代价信息时，才按原有职责读取这些属性；不要额外引入路径搜索算法。
-   不要因为新增代价字段而改变路径长度、转弯数、U
    形结构、自然障碍分布、出入口位置或其他既有地图生成结果。

## 坐标输出要求（本任务的验收重点）

找到当前输出地图坐标信息的代码，并扩展每个坐标对应的数据。具体序列化格式沿用项目已有格式，不要求更改控制台地图文本样式。

每个坐标至少应包含以下语义：

-   `X`、`Y` 或项目现有坐标标识；
-   地形类型；
-   通行属性；
-   对于可通行格：有效代价；
-   对于不可跨越格：明确的不可跨越标记。

例如，输出数据在语义上应能表达：

``` json
[
  {
    "x": 0,
    "y": 0,
    "terrainType": "Plain",
    "traversalType": "Traversable",
    "cost": 2
  },
  {
    "x": 1,
    "y": 0,
    "terrainType": "NaturalObstacle",
    "traversalType": "Impassable",
    "cost": null
  }
]
```

以上 JSON 仅为字段语义示例，不要求项目改用
JSON，也不要求改变现有输出格式。如果现有输出是
CSV、对象列表或其他格式，应在原格式中增加等价字段。

**禁止只输出坐标和地形符号，却不输出该坐标的代价/不可跨越信息。**
同时禁止只在整张地图级别输出一张代价表而无法可靠地与坐标一一对应。

## 配置与兼容性

-   尽量沿用项目已有配置入口。
-   如果需要新增代价配置，设置合理默认值，确保旧配置缺少新字段时仍可正常运行。
-   不要改变现有配置参数的含义。
-   不要改变旧有地图生成参数的默认值。
-   若增加配置会影响序列化或旧配置读取，应提供兼容默认值或迁移逻辑。
-   若项目没有特殊地形，则第一版只需支持现有地形对应的代价/不可跨越属性；不要为了演示而额外新增地形种类。

## 验证与测试

修改后至少验证：

1.  同一组输入参数下，原有地图生成机制和结构约束仍然工作。
2.  自然障碍生成逻辑未被改写；障碍位置、数量和概率没有因本次修改被有意改变。
3.  所有输出坐标都具备地形类型和通行属性。
4.  所有可通行格都具有符合规则的代价。
5.  所有不可跨越格都具有明确的阻挡状态，且不会被误当作可通行格。
6.  地形类型改变时，通行属性和代价同步改变。
7.  出入口及特殊格子的属性符合项目原有规则。
8.  内部结构路径仍然只承担原有的地图生成辅助职责。
9.  旧配置在缺少新增代价参数时仍能运行。
10. 若项目已有测试或样例，运行并报告结果；不要声称执行过未实际运行的测试。

如需比较生成结果，优先使用相同随机种子（若项目支持）比较修改前后的地图结构。若属性赋值要求不可避免地改变随机数调用顺序，应说明原因，并尽量避免这种改变。
