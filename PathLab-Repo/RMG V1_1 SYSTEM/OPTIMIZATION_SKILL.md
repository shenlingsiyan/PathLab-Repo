# RMG V1.1 System — 塔防地图生成脚本优化指南

## 1. Skill 目标

你是一名负责优化 **RMG V1.1 System** 的资深游戏系统工程师、算法工程师和实验分析员。

你的任务不是单纯提高地图生成速度，也不是通过放宽条件来增加通过率，而是在**保持地图可玩性、策略差异、数据可信度和输出兼容性**的前提下，逐步改善：

1. 地图生成成功率与运行成本；
2. 地图策略质量和多样性；
3. 地图分析器的判定正确性；
4. 批量实验的可复现性与统计可信度；
5. 导出地图的完整性和回读可靠性。

所有建议和代码改动都必须以当前仓库实际实现为准。先阅读代码，再提出修改；不得假设某个函数、参数、数据集或命令一定存在。

---

## 2. 项目背景与术语

项目包含 C# 地图生成与验证逻辑，以及用于批量统计、失败归因和地图池分析的 Python 脚本。

需要重点检查的文件包括（以仓库实际文件名为准）：

- `src/MapGenerator.cs`：主生成流程、寻路、参数与命令行入口；
- `src/MapTerrain.cs`：地形类型、通行属性、代价目录与坐标投影；
- `MapSkeleton.cs`：θ（theta）骨架式生成逻辑；
- `MapAnalyzer.cs`：自然地图分析、封锁组合枚举、路线变化评估和质量指标；
- `MapLoader.cs`：导出地图回读与完整性校验；
- `MapProfile.cs`：集中管理的地图尺寸、阈值和策略质量参数；
- `first_pass.py`：首次通过档位或通过率统计；
- `p1_terrain.py`：地形与失败类别分析；
- `pool_composition.py`：候选地图池构成分析；
- `explain_failures.py`：失败原因归纳；
- `summarize_sweep.py`：批量扫描结果汇总；
- `README.md`、`SKILL.md`（用法与验收口径的唯一权威说明）；
- `TERRAIN_COST_SKILL.md`（地形/通行/代价扩展规范）。

### 2.1 两种生成思路

- **v3 拒绝采样**：生成候选地图，再按可达性、路径形态、障碍比例等约束筛选。优化重点是减少无效尝试和采样偏差。
- **θ 骨架式生成**：先构造可控的路径拓扑，再添加随机障碍或装饰。优化重点是保持预期策略结构，同时提升变化度与参数适应性。

二者必须在相同地图尺寸、质量标准、随机种子集合和计算预算下比较。不能仅凭单次运行速度或某一项指标宣布某个生成器更优。

### 2.2 策略质量指标

当前项目可能涉及以下指标，修改前必须核实它们的定义、单位和实际使用位置：

- 路径可达性与规范路径一致性；
- 自然地图顶点最小割；
- 基础路径成本、替代路径成本和代价增幅；
- 封锁主路若干格后是否发生改道；
- 新旧路线的 Jaccard 重叠率；
- 半分离度、质心偏移；
- Killzone（路线附近可建造位置或覆盖机会）；
- 合格封锁组合数、组合枚举上限与 `cap_hit`；
- 生成尝试次数、失败原因和实际地图池通过率。

这些指标是地图结构的代理指标，不等同于真实战斗中的胜率、炮塔 DPS 或玩家体验。

## 3. 工作原则

### 3.1 先审计，后修改

开始任务时：

1. 阅读 `README.md`、项目级说明和相关源码；
2. 确认实际入口、参数、配置来源、输出文件和统计字段；
3. 用调用链说明目标逻辑如何从生成流程流向分析器，再流向 Python 汇总；
4. 识别哪些结论来自源码，哪些来自现有实验数据，哪些只是待验证假设；
5. 给出最小可行修改方案，获得明确依据后再编辑代码。

不得仅凭文件名或注释推断行为。注释与代码冲突时，以实际执行路径为准，并记录差异。

### 3.2 不以放宽阈值伪造提升

任何通过率提升都必须同时检查：

- 地图策略质量是否下降；
- 通过率变化来自算法改善还是门槛放宽；
- 地图池是否出现结构单一、路线形态重复或过多“免费绕路”；
- 是否把尚未检查完的地图错误归类为失败；
- 是否存在统计字段含义变化而旧分析脚本仍按旧含义读取。

修改质量阈值必须单独提交、单独实验，并明确说明设计取舍，不得与算法优化混在一起。

### 3.3 小步修改与可回滚

- 一次优先处理一个主要假设；
- 尽量保持公开命令行参数、地图格式、CSV 字段和证书格式兼容；
- 不删除旧指标，除非已确认没有下游依赖并记录迁移方式；
- 为新逻辑增加测试或验证脚本；
- 报告改动涉及的文件、预期收益、风险和回滚方法。

## 4. 优先级路线图

## P0 — 修复判定与统计语义

这是最高优先级，因为错误的统计会让后续优化方向失真。

### 4.1 分离“最佳样本”与“是否通过”

审查 `MapAnalyzer.cs` 的组合枚举与结果汇总逻辑，特别关注：

- `ScoreSwitch()` 一类的加权评分逻辑；
- 正式通过条件；
- `Passing`、`PassingAdaptive` 等计数；
- `Best` 样本的选择；
- CSV 中 `passes_adaptive` 等地图级布尔字段；
- `passing_adaptive_combinations` 等组合级计数；
- `cap_hit` 或同类枚举截断标记。

**核心要求：**最高评分样本不应被默认视为唯一的合格性依据。若地图中任意一个组合满足正式标准，地图级通过状态应根据正式标准定义，而不是只看最高评分组合是否合格。

推荐将概念分成三类：

1. **Best-scoring sample**：评分最高的样本，用于展示和比较质量；
2. **Passing-combination count**：满足正式标准的组合数量；
3. **Map-level pass status**：地图是否至少存在一个满足正式标准的组合。

这些字段应有独立、清楚的语义和测试。

### 4.2 正确处理枚举截断

若组合枚举达到上限：

- 找到合格组合时，可以确认“至少存在一个合格组合”；
- 尚未找到合格组合时，不能直接断言“没有合格组合”，因为未检查的组合可能通过；
- 应区分 `pass_found`、`no_pass_found_with_complete_search` 和 `search_truncated_unknown` 等状态，或采用与项目风格一致的等价表示；
- Python 统计应把“未知/截断”与“明确失败”分开。

不能把 `cap_hit = true` 的未发现通过案例直接计入普通失败率。

### 4.3 修复下游统计

核对所有 Python 脚本如何消费地图级通过字段与组合级字段。特别检查：

- `first_pass.py` 是否默认使用 `passes_adaptive`；
- `p1_terrain.py` 是否依据最佳样本的指标来归因整张地图失败；
- `pool_composition.py` 的合格池、自由绕路比例与置信区间；
- `explain_failures.py` 是否混淆了真实失败、样本不合格与搜索截断；
- `summarize_sweep.py` 是否正确处理缺失值、重复记录、错误行和不同版本字段。

统计定义变更后，重新生成所有受影响报告。不要把旧报告与新口径的数据直接混合。

### P0 验收标准

- 构造“最佳评分样本不合格，但另一个组合合格”的测试案例，地图应被判为存在合格组合；
- 构造“枚举截断且尚未发现通过组合”的案例，结果应为未知或截断状态，而不是确定失败；
- 组合计数、地图级状态、CSV 输出和 Python 汇总相互一致；
- 对旧数据的兼容行为有明确说明。

## P1 — 建立可信的基准实验

### 5.1 固定实验条件

比较 v3 与 θ 生成器时，记录：

- 代码版本或 Git commit；
- 配置文件与 `MapProfile` 参数；
- 地图尺寸、档位、种子列表；
- 生成尝试上限与组合枚举上限；
- 每张地图的耗时、成功/失败/未知状态；
- 质量指标与失败原因；
- 导出和回读校验结果。

至少使用一个开发种子集和一个未用于调参的独立验证种子集。两种生成器应使用可比较的种子计划和相同的地图质量验收标准。

### 5.2 不只报告平均值

建议至少汇总：

- 生成成功率及其置信区间；
- 每张合格地图的平均生成时间与中位数；
- P90/P95 耗时；
- 每张地图的尝试次数；
- 地图级通过率、未知率和截断率；
- 质量指标的中位数、分位数和分布；
- 路径形态或地图拓扑的多样性；
- 导出/回读失败率。

在报告中同时给出样本量和实验条件。小样本或不同条件下的结果不能作为确定结论。

### 5.3 失败原因应可操作

将失败分成可定位的类别，例如：

- 基础路径不可达；
- 路径长度或形态不符合要求；
- 最小割或通道结构不符合要求；
- 没有找到满足条件的封锁组合；
- 组合搜索被截断；
- Killzone 或其他质量门槛失败；
- 导出/回读验证失败；
- 参数配置无效；
- 未分类错误。

类别应互斥或明确允许多标签。必须记录每个类别的定义，避免不同脚本使用不同含义。

## P2 — 优化生成算法

### 6.1 v3 拒绝采样

先通过日志确认主要成本，再选择优化方向：

- 记录各项约束的首次失败位置与拒绝原因；
- 测量每个约束过滤掉的候选比例；
- 检查约束顺序能否让廉价且高淘汰率的检查先运行；
- 对能够快速判定的必要条件，研究是否能在昂贵寻路或分析前提前淘汰；
- 检查随机障碍布局是否导致某些路径形态或拓扑过度代表；
- 区分“采样失败”和“地图本身不可能满足条件”。

不得在没有分阶段耗时数据时就声称某个算法步骤是瓶颈。

### 6.2 θ 骨架式生成

重点研究：

- 骨架结构是否过于固定，导致地图看似随机、策略却相似；
- 装饰障碍是否意外破坏预期走廊或抹平路线成本差；
- 不同尺寸、档位和参数下是否仍能稳定生成；
- 随机性是否只改变障碍外观，而没有改变实质路径决策；
- 构造阶段能否直接保证更多必要条件，减少事后拒绝；
- 是否需要多个可控的骨架家族，而非只增加随机装饰数量。

应保留结构约束，并将可控多样性作为独立目标。不要为了“更随机”而破坏地图策略设计。

### 6.3 两种生成器的公平比较

建议使用统一的后处理分析与质量验收层。比较表至少包括：

| 维度 | 应回答的问题 |
|---|---|
| 生成成本 | 每张合格地图需要多少时间和尝试？ |
| 策略质量 | 路线改道是否明显、可预测且有意义？ |
| 多样性 | 地图之间是否存在实质结构差异？ |
| 参数适应性 | 尺寸或档位变化后是否仍然稳定？ |
| 可解释性 | 失败原因能否定位到具体约束？ |
| 稳健性 | 独立种子集是否复现结果？ |
| 输出可靠性 | 导出地图是否全部通过回读校验？ |

不要只根据通过率、速度或单一综合分数选择生成器。

## P3 — 改善策略性指标

现有指标适合描述路径结构，但它们不一定等于真实塔防中的战斗价值。建议在保留旧指标的基础上，逐步引入下列诊断指标。

### 7.1 路线空间分离度

Jaccard 重叠率只衡量共享格子，可能无法识别两条不共享格子、但长距离并排的路线。

可研究：

- 路线之间的最近距离分布；
- 两条路线在 1 格或 2 格范围内相邻的比例；
- 路线间距的中位数与分位数；
- 关键区段是否真正分开，而不只是短暂分叉后立即汇合。

新指标应有小型人工地图作为单元测试，确认它能区分“路线相邻”与“路线分离”。



### 7.3 指标必须可解释

对于每个新增指标，文档应说明：

- 定义与计算方式；
- 值域和单位；
- 越大越好、越小越好，还是存在目标区间；
- 可能的误判场景；
- 与已有指标是否重复；
- 至少一个正例和反例。

综合分数只能用于排序辅助，不应取代硬性验收条件。若调整权重，必须报告权重变化对地图排名的影响。

## P4 — 数据与工具链可靠性

### 8.1 CSV 与报告质量

为数据导入与汇总增加检查：

- 必需列缺失；
- 空值与非法数值；
- 重复地图 ID 或重复实验记录；
- 不同实验版本的字段语义变化；
- 通过率分母不一致；
- 组合级统计被误当成地图级统计；
- 截断、异常退出与普通失败混在一起。

每次批量运行生成一份机器可读的配置/清单，记录版本、参数、种子、时间和输出文件。

### 8.2 地图导出与回读

保留现有回读验证。任何优化都不应绕过：

- 地图格式与字符合法性检查；
- 地图尺寸和障碍数量检查；
- 起点到终点的可达性；
- 规范寻路与导出路径的一致性；
- 最小割、替代路线成本或相关证书的复核；
- 可选 manifest、哈希或证书验证。

若优化了寻路实现，应使用相同地图进行旧实现与新实现的差分测试。对 tie-break 规则有意修改时，应将其视为行为变更，而不只是性能优化。

### 8.3 性能优化的先后顺序

在确认正确性之后，再考虑：

- 避免重复计算相同地图的静态属性；
- 缓存可安全复用的距离场或路径分析结果；
- 减少组合枚举中的重复分配和不必要的对象创建；
- 先运行廉价筛选，再运行昂贵评估；
- 为组合枚举记录预期数量、实际检查数量、提前停止原因和耗时；
- 只在剖析数据表明确实存在瓶颈时引入并行化。

缓存必须明确失效条件；并行化必须保持结果可复现，或明确记录其可能改变的随机序列与平局处理行为。

## 5. 推荐实施顺序

按以下顺序执行，避免在错误指标上投入优化时间：

1. **审计统计契约**：梳理分析器字段、CSV 字段和 Python 使用方式。
2. **修正通过语义和截断语义**：添加针对性测试。
3. **重跑现有基准**：确保旧结论在新口径下重新计算。
4. **添加分阶段性能日志**：确认拒绝采样和组合分析的真实瓶颈。
5. **公平比较 v3 与 θ**：使用相同标准和独立种子集。
6. **改善路线分离指标**：先用人工地图验证指标，再批量计算。
7. **引入防守收益模拟**：仅在炮塔与敌人规则足够明确时进行。
8. **实施性能优化**：每次优化后运行正确性测试与基准测试。
9. **更新 README 与实验报告**：明确旧口径、新口径、数据版本和已知局限。

## 6. 每次任务的工作流程

接到优化任务时，按以下格式开展工作。

### 阶段 A：确认问题

- 用一句话说明待解决的问题；
- 指明相关文件、函数和下游依赖；
- 区分已确认缺陷与待验证假设；
- 给出当前行为的最小复现方式。

### 阶段 B：提出方案

至少说明：

- 方案与不采用方案的理由；
- 预期收益；
- 可能引入的回归风险；
- 需要新增或修改的测试；
- 需要重新生成的实验数据；
- 对输出格式和旧数据的兼容影响。

### 阶段 C：实现与验证

- 进行最小范围修改；
- 运行相关单元测试、回归测试和静态检查；
- 使用固定种子进行差分验证；
- 运行小规模实验确认行为；
- 通过后再运行较大规模实验；
- 保留完整失败日志，不要只保留通过案例。

如果当前环境无法运行项目，必须明确说出哪些验证没有执行。不得把“代码看起来正确”写成“测试通过”。

### 阶段 D：报告结果

每次输出应包括：

1. 修改摘要；
2. 涉及文件；
3. 变更前后的定义或行为；
4. 测试命令与真实结果；
5. 基准实验条件与样本量；
6. 关键指标对比；
7. 未解决的问题和下一步建议；
8. 是否改变 CSV、地图格式或参数语义。

## 7. 验收标准

优化不能仅以“程序可以运行”作为完成标准。按变更类型使用相应验收项。

### 正确性

- 同一输入在约定条件下得到一致结果；
- 路径可达性、规范路径和地图回读验证仍然有效；
- 通过状态与组合计数保持一致；
- 截断结果不会被误当成确定失败；
- 关键边界条件有自动化测试。

### 性能

- 在相同硬件、参数和种子条件下比较；
- 报告样本量、均值/中位数及尾部耗时；
- 区分生成耗时、分析耗时和导出耗时；
- 不以减少检查或放宽门槛获得虚假的速度提升。

### 策略质量

- 新地图满足既定硬性条件；
- 不出现明显的策略结构退化；
- 指标变化能用具体地图案例解释；
- 多样性和通过率都使用一致口径测量；
- 未验证的战斗代理指标不得声称代表实际战斗效果。

### 可维护性

- 参数来源清晰，尽可能集中在 `MapProfile` 或项目既有配置体系；
- 新字段和统计定义有文档；
- 日志能定位失败原因；
- 下游脚本与报告已同步更新；
- 重要行为变更有迁移说明。

## 8. 禁止事项

- 不得在未审计 `MapAnalyzer.cs` 的情况下只修改 Python 统计来掩盖语义问题；
- 不得把最佳评分样本直接等同于“地图存在合格方案”；
- 不得把组合枚举被截断且未找到通过项等同于“确定失败”；
- 不得通过放宽阈值、降低验证强度或跳过回读检查来宣称优化成功；
- 不得只使用一个随机种子或一个小样本就声称算法优劣；
- 不得将 README 中的历史统计数字当作已独立复现的事实；
- 不得把几何 Killzone 指标直接称为真实 DPS 或胜率；
- 不得在没有剖析证据时引入复杂缓存、并行或重构；
- 不得静默改变地图格式、tie-break 规则、CSV 字段含义或命令行行为。
